# Production renderer routing and Windows asset preservation

Follow-up to `2a0596e6`, 2026-11-14. No deployment or Prism installation.

## Root causes and fixes

1. The new cast clips loaded and sampled correctly, but `RiftGuardianModelRenderer.normalizeAnimationId` still called a second `authoredClipFor` switch before `RiftGuardianModel.setupAnim`. It rewrote CAST_CHARGE/CAST_RELEASE/RECOVERY/FINAL_STRIKE to CHEST_STRIKE. This bypassed the actual clips and changed playback-rate identity. The renderer now preserves the canonical action; the animation player is the sole owner of clip lookup/fallback. Existing aliases and explicit UNKNOWN handling remain.
2. The eight private mesh JSON files lacked a `.gitattributes` rule. A real `core.autocrlf=true` export changed all eight files. CI run 43529936592 built a 17,064,994-byte client instead of the pinned 17,064,823-byte client. A targeted `-text` rule preserves generated bytes. The Windows-export test now exercises both original generated rigs and all eight spell meshes.

## Behavioral reproduction

The production-renderer JUnit probe (not just the clip loader) failed twice before the fix: CAST_CHARGE normalized to CHEST_STRIKE, and the sampled pose did not match the authored cast. The repaired probe checks the renderer→model→pose chain for charge, release, recovery and Final Strike in every one of the six phases. Both tests pass with the repair.

The old Windows-export probe reported eight mismatches. The extended repository test passes with the exact-byte rule. The artwork, geometry and original supplied model assets were not repainted to mask the packaging failure.
