# CopiMine Client Bridge v4 Design

## Goal

Allow the CopiMine 26.3 client to apply protected server-to-client controls and visuals only when a packet was signed by the pinned CopiMine Ed25519 key for the current client connection. Missing or mismatched server signing material must disable protected sends without a v3 fallback.

## Accepted constraints

- The client pins key ID `copimine-bridge-20261015-v1` and the supplied X.509 Ed25519 public key. Its SHA-256 fingerprint is `2dadc8a92218471ad51721299974968c326e9ffd3b08ae8dd1e50ec7079dff62`.
- Public key Base64 X.509 DER: `MCowBQYDK2VwAyEAlud9gEV0EMTMJPDo5bQSDpd+giw+SD6/mpli1wr3l54=`.
- The PKCS#8 private key stays in the external protected file and never enters source, logs, build artifacts, resource packs, or Git.
- The Paper signer reads the key-file path from `COPIMINE_CLIENT_BRIDGE_PRIVATE_KEY_FILE`; no path or private-key contents are logged. The file is read at plugin startup. Missing, unreadable, malformed, or mismatched keys fail closed.
- Use Ed25519 with the domain-separated `BridgeSigningPolicy` and exact packet body bytes.
- No unsigned protocol-v3 mutation is accepted after the v4 client ships.
- Each new client connection receives 32 cryptographically random bytes from the client CSPRNG, encoded as canonical Base64URL without padding (exactly 43 ASCII characters). A disconnect, player UUID change, or server switch clears the nonce, authenticated streams, pending main-thread mutations, and replay counters.
- Tests use generated ephemeral key pairs only. Native Minecraft evidence must be reported separately from automated tests.

## Protocol and trust flow

Two channels have distinct roles:

- The existing `copimine:client_bridge` protocol-v3 channel remains only for the current client-mod challenge/hello, capabilities update, heartbeat, server PING acknowledgement, and client-originated visual ACK/FINISHED/ERROR. It remains protocol 3 and keeps its existing version, challenge-session, and capability checks. In the v4 client, every protocol-v3 server-to-client End Event mutation and every protocol-v3 Narcotics visual start/stop/clear is ignored unconditionally. The v3 PING only completes the client-mod handshake; it is not authority to mutate client state.
- The new `copimine:client_bridge_v4` channel carries v4 binary control records and signed server-to-client envelopes. Protected state changes are accepted only on this channel after signature and session validation.

The client creates one 32-byte CSPRNG connection nonce when a new Minecraft play connection opens, before it receives any challenge. It encodes the nonce as canonical Base64URL without padding (exactly 43 ASCII characters). A v3 challenge does not rotate this nonce. The client sends v4 records only after the existing v3 challenge/hello exchange has completed and it has accepted a PING whose session UUID equals its current v3 challenge UUID. On the server, CopiMineNarcotics owns the authoritative ClientModSessionRegistry, the external key loader, and the BridgeSigner. It creates a random, non-reused connection epoch on join, records a v3 session only after validating the pending challenge response, clears that entry on quit, rejection, required-version change, and plugin shutdown, and publishes both Bukkit services from the shared pure-Java API in tools/minecraft-26.3/protocol. The session API exposes current(playerUuid) and requestFreshChallenge(playerUuid); the optional returned record contains player UUID, verified challenge/session UUID, accepted client version, and opaque connection epoch. The signer exposes sign(nonce, recipient, streamId, counter, issuedAtMillis, expiresAtMillis, exactBody), returning either a raw signature or unavailable, and never exposes the private key. CopiMineEndEvent resolves both services through a soft dependency; if either is absent, the plugin may continue unrelated event gameplay, but all v4 controls and client-dependent mechanics stay disabled. It must compare the current connection epoch, UUID, and verified session before accepting any v4 request and must never trust the v3 session UUID from an End Event hello. A v4 control_hello binds the client nonce and hello ID to the registry verified session and current connection epoch. Each sender then maintains its own authenticated stream under that shared binding. A new v3 challenge session on the same play connection is accepted only after the registry validates the fresh challenge response; it invalidates each old sender stream, readiness, outstanding request ID, counter, and queued mutation while retaining the connection nonce, local connection epoch, per-connection seen-stream-ID history, and generation high-water marks. The client then starts new sender streams under the verified session without reusing any stream ID already seen during that play connection. Either Paper sender must call requestFreshChallenge when its bridge state is restarted so no sender resumes after losing its counters. The protocol API classes are bundled only in Narcotics and must not be duplicated in the End Event JAR, so the Bukkit service contract has one class identity. Disconnect, player UUID change, or server switch clears the nonce, authenticated streams, per-sender readiness, request counters, seen-stream-ID history, generation high-water marks, queued mutations, and replay state.

Every call to `requestFreshChallenge` immediately invalidates the current registry entry and notifies both sender services before the new challenge is sent. Each sender checks `registry.current(playerUuid)` against the stream's player UUID, verified session, and connection epoch before every signed send and every accepted client request. If the entry is absent or differs, the sender immediately retires its cached stream, readiness, pending requests, and queued sends, and blocks protected mechanics until a newly verified session completes a fresh per-sender handshake. This prevents a surviving sender from using stale readiness during another plugin's challenge-recovery window.

All client-to-server v4 records start with `u8 protocol=4`, `u8 type`, `u8 nonce_length=43`, the 43 nonce ASCII bytes, `player_uuid[16]`, and `client_mod_session_uuid[16]`. The nonce and UUID must match the live play connection and current verified v3 client-mod session in the shared registry. Reject records over 1,024 bytes, unknown types, malformed lengths, noncanonical values, nonce/player/session mismatches, trailing bytes, and out-of-order request counters before they can change server state. A well-formed request with a syntactically valid but stale sender stream ID is rejected after consuming its expected counter, as specified below. These records do not carry Ed25519 signatures because they are requests from the connected client, not server-authority assertions. Each sender has one serialized inbound counter/outbox per `(connection epoch, player UUID, nonce, client_mod_session_uuid)`. For a counter-bearing record, protocol/type/length validity, a live player/nonce/session/epoch binding, and routing to this sender are checked first. The sender then requires the next expected counter and consumes it before checking the named stream ID/current stream, readiness, or gameplay policy. Thus a well-formed request with a syntactically valid stale stream ID is rejected but still consumes its expected counter. A malformed record, wrong live binding, record routed to the other sender, or wrong/gapped/reused-with-different-bytes counter is rejected without advancing it. Exact duplicate bytes at the last consumed counter may replay only the cached idempotent response; the same counter with different bytes or a counter gap never changes gameplay state. Counters are positive signed 64-bit values, never wrap, and reaching `Long.MAX_VALUE` disables that sender's v4 features until a new connection or newly verified v3 session.

Type `0 control_hello` appends `client_hello_id[16]`, a fresh CSPRNG request ID retained for the current `(connection epoch, nonce, client_mod_session_uuid)`. A duplicate hello with the same nonce, player UUID, session UUID, and hello ID is idempotent and must not rotate an active stream. The sender may retransmit the exact cached signed acknowledgement only while that hello remains current; the client accepts it at most once. If an acknowledgement is missing, the client retires that hello ID locally and uses a targeted reopen request with a new request ID and no expected stream ID. A different nonce cannot replace the nonce already bound to a live play connection. A changed client-mod session is accepted only after the shared registry validates a fresh v3 challenge for that session; it retires each sender's prior session stream, resets that sender's request counter, and starts fresh sender acknowledgements correlated to the new hello ID. Each sender rejects a new hello ID for the same active `(connection epoch, nonce, session)`; stream replacement in that session must use type 2.

Type `1 prisoner_ability_request` appends a positive `i64 request_counter` scoped to the End Event sender and verified client-mod session, `u8 stream_id_length=22`, the 22-byte current End Event stream ID, `event_uuid[16]`, positive `i64 generation`, ASCII `string ability_id`, `u8 target_present`, and `target_uuid[16]` only when the flag is 1. The flag is exactly 0 or 1. The sender's request counter begins at 1 for the first sender-addressed v4 request and increments by exactly one for each End Event `sender_ready`, reopen, or ability request; `sender_ready_confirm` is an idempotent receipt and does not consume a request counter. It survives stream replacement and resets only when the verified v3 client-mod session or play connection changes. The server first validates the live nonce/player/session/epoch binding and request structure/counter. It consumes a valid expected counter before checking whether the named End Event stream is current, readiness, or gameplay authorization gates. If the stream is `READY_PENDING_CONFIRM`, a structurally valid ability request is rejected without applying its ability, but its counter remains consumed so a subsequent reopen stays synchronized. Once ready, the server also checks exact event/generation, permission, cooldown, and target before applying existing ability policy. A request from an old connection, stream, client-mod session, or event generation is rejected.

Type `2 stream_reopen_request` appends a positive `i64 request_counter` scoped to the named sender, `u8 sender` (`1=end_event`, `2=narcotics`), `u8 expected_stream_id_length` (`0` or `22`), the expected stream ID bytes when the length is 22, and a fresh `request_id[16]`. A zero-length ID requests recovery only when the client has not accepted a `hello_ack` and the sender has not accepted `sender_ready` for the current stream; the sender retires any unconfirmed stream it issued and creates a replacement. A 22-byte ID requests replacement only when it exactly names that sender's current stream that the client retired, or its most recently retired stream when the server had already retired it. The request retires only the named sender's stream, clears its readiness, and never rotates another stream. The response `hello_ack` includes `request_kind=1` and this exact request ID; the client accepts it only while that ID is the one outstanding for this sender. Retransmitting the same request bytes and counter is idempotent only while that request remains the sender's last consumed request and its cached response stream is still current; the server may retransmit that exact cached ACK but must not rotate again. A new request uses the next per-sender counter and a new request ID. Requests are rate-limited to one new reopen per sender per second; exact retransmissions of the last request do not consume another slot. The client uses bounded backoff up to 30 seconds. A wrong ID, reused counter with different bytes, gapped counter, or stale request does not rotate any stream.

Type `3 sender_ready` appends a positive `i64 request_counter` scoped to the named sender and verified client-mod session, `u8 sender`, `u8 stream_id_length=22`, the 22-byte stream ID from that sender's verified `hello_ack`, a fresh `request_id[16]`, and `ack_envelope_sha256[32]` (SHA-256 over the exact serialized signed `hello_ack` envelope bytes). The server accepts it only if the envelope digest, stream, session, request ID, and counter match the ACK it issued. It then sends a signed `sender_ready_ack` on that stream at counter 2, containing the sender, session UUID, ready request ID, and ready request counter, and stores that envelope's `expires_at_ms`. The server remains in `READY_PENDING_CONFIRM` and must not start protected mechanics or send application data yet. After validating this correlated signed ACK, the client marks the sender locally ready and sends type `4 sender_ready_confirm` next in that sender's serialized client outbox. After the common request header, the confirmation is exactly `u8 sender, u8 stream_id_length=22, stream_id[22], ready_request_id[16], i64 ready_request_counter, ack_envelope_sha256[32]`, where the digest covers the exact serialized signed `sender_ready_ack` envelope. It has no `request_counter`: it is a replay-safe, idempotent receipt bound to the current stream and ready exchange, not a sequenced operation. The server accepts its first copy only for the current pending ready exchange while `now_ms < stored_ack_expires_at_ms`, then advances to `READY`; at or after expiry it retires the pending stream and rejects the confirmation. A byte-identical repeat is a no-op while the same stream and ready exchange remain current, including after readiness; a different confirmation or one from a retired stream is rejected. Only after accepting the confirmation may the server start dependent mechanics or send counter-3 application data. The client retries the identical confirmation if no subsequent signed traffic proves the stream is active. If the signed ACK expires, is lost, or fails correlation, the client stops confirmation retries, retires the local pending stream, rejects application data, and recovers with a sender-specific reopen request naming the retired 22-byte stream ID. The reopen uses the next unused sender request counter after all earlier counted requests for this sender and session; the uncounted confirmation consumes none. This value is correct whether the confirmation was lost or accepted, so expiry recovery cannot desynchronize request counters. The server accepts this targeted reopen for either its still-current ready stream or its most recently retired pending stream, retires only that named stream, and creates a fresh stream without resetting the sender request counter. This is a cooperative receipt, not client attestation: without a client-authentication key, a modified client can read and hash the ACK and forge this request without verifying the signature. The server treats it only as a receipt that gates normal operation for a cooperative client; it never substitutes for server-side ability, permission, target, cooldown, or event-generation checks, and it is not evidence that a client-side effect was applied. An official client with a wrong pinned key does not send this confirmation, but protection against a deliberately modified client is outside this server-authentication protocol. Readiness is independent for `end_event` and `narcotics`; an unavailable signer or an official client that rejects its key leaves only that sender disabled. The End Event sender requires server readiness before starting any mechanic that depends on a client-side control or prisoner mutation. Narcotics requires server readiness before starting or refreshing a remote visual.

End Event ability, reopen, and `sender_ready` records share one strictly increasing request counter per End Event sender and verified client-mod session. Narcotics reopen and `sender_ready` records use a separate strictly increasing counter per Narcotics sender and verified client-mod session. `sender_ready_confirm` is an uncounted receipt bound to one current ready exchange and is excluded from both counters. Each Paper plugin ignores records addressed to the other sender and does not advance its own counter for them. `control_hello` is idempotent and has no counter. Reconnect and a newly verified client-mod session reset these counters; stream replacement alone does not reset the counter for that sender. A Paper bridge restart must force a fresh v3 challenge/session before it resumes v4 traffic so a client and server cannot disagree about request-counter state.

Each Paper sender creates an independent 128-bit CSPRNG stream ID for each accepted `(player UUID, connection nonce, client-mod session)`, encoded as canonical Base64URL without padding (exactly 22 ASCII characters). It sends a signed `hello_ack` with counter exactly 1 before any protected message. The acknowledgement body identifies its fixed sender (`1=end_event`, `2=narcotics`) and echoes the current `client_mod_session_uuid[16]`; unknown sender IDs are rejected. Each sender serializes writes per player and increments the stream counter by exactly one for every signed message. End Event and Narcotics use separate stream IDs and counters. A sender never resets a counter for an existing stream; it creates a new stream before counter overflow or after a stream must be retired. A stream replacement creates a fresh stream ID and counter 1, then waits for `sender_ready` before sending state. It must not resend counter 1 on an existing stream. The server and client each retain at most 256 stream IDs per sender per connection; when that bound is reached, that sender fails closed until reconnect. Reuse of a stream ID seen earlier on the same connection is rejected.

When a valid acknowledgement replaces an active stream, the client atomically retires that sender's old stream and all state owned by it before installing the new stream. For End Event only, the exact active `(event_uuid, generation)` context and its signed arena bounds survive a stream replacement so the new stream can reassert that same context; all other End Event state owned by the retired stream is cleared. The per-connection generation high-water marks survive stream replacement, unbind, and event replacement. `CONTEXT_UNBIND` clears the active context and its bounds. A new event bind atomically replaces the active context and bounds. The new stream must reassert the exact active context with `CONTEXT_BIND` before any other End Event mutation. Narcotics stream replacement retires all remote visuals owned by its old stream. After the client confirms a new Narcotics stream, the server resends a snapshot of still-active visuals using their same logical visual instance IDs and fresh command sequence/counter values; the client treats them as new instances owned by the new stream.

### Signed message bodies

All bodies are binary and have one exact schema selected by the signed sender and body type. The outer envelope's `body_length` counts every body byte. The signature covers those bytes unchanged; verification never decodes and re-encodes them. Integers are big-endian. Body strings are ASCII only, encoded as a two-byte unsigned byte length followed by the bytes; reject NUL, controls, non-ASCII bytes, overlong values, and invalid identifier syntax. The general string limit is 4,096 bytes; enum/identifier fields are limited to 128 bytes, phase and dimension values to 256 bytes, and bounded player lists to 4,096 bytes. This is byte-for-byte the ASCII subset of Java `DataOutputStream.writeUTF`, which keeps Paper's existing ASCII identifiers interoperable without accepting modified-UTF aliases. UUIDs are 16 raw bytes in most-significant then least-significant 64-bit order. A decoder must consume the whole body, reject unknown type codes, reject non-finite floats, reject values outside the listed bounds, and reject any nonzero or nonempty reserved fields.

`hello_ack` is exactly `u8 schema=1, u8 type=0, u8 sender, client_mod_session_uuid[16], u8 request_kind, request_id[16]`, where sender 1 is `end_event` and sender 2 is `narcotics`. `request_kind=0` correlates to `control_hello`; `request_kind=1` correlates to `stream_reopen_request`. The session UUID, request kind, and request ID must equal the client's current verified session and single outstanding request for that sender. It is accepted only at stream counter 1 and only if its stream ID has never been seen for this connection. No protected body can precede it.

`sender_ready_ack` is exactly `u8 schema=1, u8 type=255, u8 sender, client_mod_session_uuid[16], request_id[16], i64 ready_request_counter`. It is accepted only at counter 2 on the acknowledged stream and only when every field matches the client's one outstanding `sender_ready` request. Type 255 is reserved for this common bridge-control body and is invalid on any other message. The first End Event or Narcotics application mutation uses counter 3 or later, and the server sends it only after it validates the client's `sender_ready_confirm`. The client applies no application mutation before validating `sender_ready_ack` and queueing the exact correlated confirmation ahead of later requests on the same sender outbox; confirmation retries do not consume or advance that sender's client request counter.

An End Event body is one fixed record in this order: `u8 schema=1`, `u8 type`, `u32 message_schema=4`, `i64 generation`, `i64 body_timestamp_ms`, `event_uuid[16]`, `string instance_id`, four `u8` flags (all zero), `u32 supported_effect_count` (zero), `string control_id`, `string visual_id`, `u32 duration_ms`, `f32 progress_or_intensity` (finite, 0..1), `u32 health`, `u32 max_health`, `string subject_or_mode`, `string clear_policy`, two reserved empty strings, and `string status`. The timestamp must equal the outer `issued_at_ms`; generation is positive and at most `Long.MAX_VALUE - 1` (the client reserves `Long.MAX_VALUE` as an internal sentinel). `event_uuid` is the event ID that the existing client managers consume. `subject_or_mode` is a type-specific string slot: its exact grammar and meaning are defined for each message type below, so it is never inferred or remapped from another field. For control leases, `instance_id` is the unique per-lease UUID used by both START and STOP, `control_id` is the control enum, and SWAP's target UUID is carried in `subject_or_mode`; the legacy source label is not a lease ID and is not emitted in v4. For any message type, fields not listed as required are empty or zero. All duration_ms values in End Event records are at most 600,000, except `END_WORLD_BEAM`, which requires 1..2,000 ms. `END_WORLD_BEAM` width is finite and within 0.02..0.45 inclusive; the client retains at most 64 active beams and 256 beam instance-version records per connection, and the decoder and beam manager reject a new instance or clear-fence operation that would exceed either limit without clamping, evicting, or clearing existing beams. `instance_id` is at most 128 ASCII bytes and uses a type-specific grammar: control lease IDs and prisoner recipients are canonical UUIDs; world-beam instances are exactly `<event_uuid>:<generation>:world:<key>`; other event render instances match `[A-Za-z0-9_.:-]{1,128}` and are scoped to the signed event generation. `subject_or_mode`, `clear_policy`, `status`, phase strings, UUID strings, dimensions, and delimited lists use strict per-field limits; nonempty lists contain canonical UUIDs, no duplicates, and no empty elements. A canonical UUID string is lowercase `8-4-4-4-12` hexadecimal with hyphens; raw UUID fields are 16 bytes in network order. A canonical nonnegative decimal integer is `0` or a nonzero digit followed by digits, with no sign or leading zero; a positive integer is a nonzero digit followed by digits. End Event dimension tokens are exactly `overworld`, `the_nether`, or `the_end`, matching the current Paper sender. Echo frame dimensions are lowercase resource locations matching `[a-z0-9_.-]+:[a-z0-9_/.-]+` and are at most 64 ASCII bytes. A world key matches `[A-Za-z0-9_-]{1,64}`. A beam point coordinate is finite ASCII decimal with exactly three fractional digits, no exponent or leading zeroes except `0`, and absolute x/z at most 30,000,000 and y in `[-4096,4097)`; both coordinates are still constrained by the active context bounds below.

For `CONTEXT_BIND`, `subject_or_mode` is exactly `<end_dimension>|<minX>,<minY>,<minZ>|<maxX>,<maxY>,<maxZ>`. Bounds are canonical signed decimal integers (`0` or an optional `-` followed by a nonzero decimal integer, with no `+`, leading zeroes, or `-0`), each minimum is <= its maximum, and the box is the configured event arena's inclusive block-coordinate AABB, matching Paper's `getBlockX/Y/Z()` checks. X/Z bounds are within `[-29,999,998,29,999,998]`, and Y bounds are within `[-4096,4096]`. Compute each inclusive span with checked signed 64-bit subtraction and addition; reject nonpositive or unrepresentable spans. The inclusive volume must be in `(0,262,144]`, checked with widened 64-bit arithmetic and division guards before multiplication so no intermediate can overflow; reject a bind on any overflow or volume excess. There are no independent width, depth, or height caps beyond the coordinate ranges and total-volume limit. The server sends the configured arena bounds; it never derives bounds from an untrusted client value, and it must not start dependent mechanics until the context bind is successfully sent. The client stores this signed AABB only with the active event context, retains it through stream replacement of that same active context, clears it on unbind, and atomically replaces it on a new event bind. It rejects a bind whose bounds, volume, or dimension are malformed. For `END_WORLD_BEAM`, `subject_or_mode` is exactly `<end_dimension>|<key>|<startX>,<startY>,<startZ>` and `clear_policy` is exactly `<endX>,<endY>,<endZ>|<RRGGBB>`. Both points must be in the active dimension, and `floor(x)`, `floor(y)`, and `floor(z)` for each endpoint must lie within the corresponding inclusive integer block bounds. Thus the world-space coverage is `[minX,maxX+1) × [minY,maxY+1) × [minZ,maxZ+1)`, including the full final block and excluding its upper face. The RGB value is exactly six uppercase hexadecimal digits. This preserves both endpoints from the current Paper sender; it does not drop beam geometry.

For boss/entity bind and phase types, `subject_or_mode` is exactly a canonical UUID. `CONTROL_START` uses `control_id` exactly `REVERSE` or `SWAP`; `subject_or_mode` is empty for `REVERSE` and a canonical target UUID for `SWAP`. Its `instance_id` is a canonical UUID unique to that control lease, reused only for an idempotent START refresh and the matching STOP; the legacy `wave2-hunt-mark` source label is not sent. `END_PLAYER_STATE` uses `subject_or_mode` exactly `<dimension>|wave<1 or 2>|<positive cycle>` for `ACTIVE` and `CLEAR`, where dimension is one of the End Event dimension tokens. `END_FOG_STATE` uses `<dimension>|wave5|<positive cycle>` only for `ACTIVE`; `CLEAR` and `SUSPEND` require an empty `subject_or_mode` and zero duration/intensity. `END_PRESENTATION_RESUME` uses one of the End Event dimension tokens. Prisoner state uses `subject_or_mode` for a canonical nonnegative decimal death count; `clear_policy` contains exactly four canonical nonnegative millisecond cooldown values separated by `|`; `status` is `PRISONER_TARGETS_V1|<support UUID CSV>|<turncoat UUID CSV>`, with at most 32 UUIDs in each list and a sender-enforced 32-item cap. For `END_PRISONER_RESUME`, `END_PRISONER_STATE`, and `END_PRISONER_CLEAR`, `instance_id` must be a canonical UUID equal to the envelope recipient UUID before any mutation is applied.

Echo types use a canonical actor UUID in `subject_or_mode`; their `clear_policy` frame is exactly `<owner_uuid>|<epoch>|<frame_sequence>|<pose>|<sprinting>|<hand>|<use_elapsed>|<use_duration>|<swing_serial>|<hurt_serial>|<death_ticks>|<equipment_version>`. `owner_uuid` is the server-authored owner of the disposable probe and must remain identical for every frame in that duel binding; it must differ from the actor UUID. The envelope recipient may be the owner or a server-authorized visual observer, as the current probe deliberately sends presentation to nearby capable viewers. The client stores this data only as an event/generation-bound visual probe and never uses it for local control, ownership authority, or duel completion. Epoch and frame sequence are positive canonical decimals in `[1,Long.MAX_VALUE]`; for one actor and epoch, every state/remove frame has a strictly increasing frame sequence. Equipment version, swing serial, hurt serial, and death ticks are nondecreasing between frames for that actor and epoch. Epochs for a re-created actor binding must increase; a newer epoch resets its frame-sequence and presentation-counter comparisons, while a stale or reused epoch is rejected. A probe must stop publishing and retire its actor before any sequence or counter increment would exceed its field maximum; counters never wrap, and the server must fail closed if no higher valid epoch can be allocated. Pose is `STANDING` or `CROUCHING`; hand is `NONE`, `MAIN`, or `OFF`; sprinting is exactly `0` or `1`; use elapsed/duration are canonical nonnegative decimals with duration <=72,000 and elapsed <= duration; `NONE` hand requires duration 0; swing and hurt serials are nonnegative values up to `Long.MAX_VALUE`; equipment version is a nonnegative integer up to 2,147,483,647; death ticks are 0..20. Dimension is a canonical namespaced `dimension_id` with length <=64. The client caps active actors at 32 globally, retains at most 128 actor entries (including removed entries), and retains at most 128 removed-before-bind tickets per connection. `END_ECHO_*` remains the disposable presentation probe only; it does not enable the deferred official personal Echo duel.

For `END_ENTITY_PHASE`, `visual_id` is either one canonical `BossAnimationId`, one wave pose token (`WAVE_COMBAT`, `WAVE_WINDUP`, `WAVE_RELEASE`, `WAVE_RECOVER`, `WAVE_FROZEN`) on an allowed wave visual, one ritual caster token (`RITUAL_CHANNEL`, `RITUAL_WINDUP`, `RITUAL_RELEASE`, `RITUAL_COMBAT`) on `END_RIFT_RITUAL_CASTER_V1`, or a tentacle phase. Canonical `BossAnimationId` values are `IDLE_BREATH`, `RUN`, `MELEE_SWIPE`, `CHEST_STRIKE`, `GROUND_SLAM`, `MARK_CONTROL`, `SUMMON_CHANNEL`, `HURT`, `PHASE_TRANSITION`, `FINAL_STRIKE`, `DYING`, `TELEPORT_RIP`, `CAST_CHARGE`, `CAST_RELEASE`, `CAST_IMPACT`, `RECOVERY`, `SPELL_VOID_BLAST`, `SPELL_RIFT_PROJECTILE`, `SPELL_RIFT_ARROWS`, `SPELL_ARROW_SALVO`, `SPELL_VOID_MARK`, `SPELL_SUMMON_SERVANTS`, `SPELL_SUMMON`, `SPELL_RIFT_OBELISKS`, and `SPELL_ARENA_INFERNO`. Tentacle visual phases use `<animation>|t=<nonnegative event tick>|health=<FULL|DAMAGED|CRITICAL|DEAD>[|target=<canonical UUID>]`; animation is one of `EMERGING`, `READY`, `TELEGRAPH_GRAB`, `GRAB_SUCCESS`, `HOLD`, `THROW`, `MISS_RECOVERY`, `HIT_RECOVERY`, `DYING`, `DEAD_RESPAWN`, `RETRACT`, `SPAWN_UNDER_PLAYER`, `SHIELD_CHANNEL`, `RECOVERY`, `IDLE`, `EMERGE`, `GRAB_MISS`, `HURT`, or `DEATH`. Boss phases use a canonical `BossAnimationId`. Boss bars use `<phase>|<cast state>`, where phase is `AWAKENING`, `HUNT`, `RIFT`, `OVERLOAD`, `RAGE`, or `LAST_SEAL` and cast state is `NONE`, `TELEGRAPHING`, `EXECUTING`, or `RECOVERY`. Float progress/intensity are finite IEEE-754 binary32 values in `[0,1]`; health/max_health are at most 2,000,000,000, and a boss bar requires health <= max_health and max_health > 0. The v4 typed encoders populate only fields specified by each row; they must not carry forward nonempty defaults from the legacy generic writer.

The client accepts event mutations only after `CONTEXT_BIND` and only when event UUID and generation exactly match the active context. Any bind that establishes a context after unbind or changes the generation for an event UUID already seen on this connection must use a generation greater than that UUID's high-water mark and atomically clear prior End Event state. A new event UUID may bind any positive generation. The client retains per-connection generation high-water marks across unbinds, stream replacement, and event replacement, subject to the connection cleanup rule. It retains the signed arena bounds only for the exact active context across stream replacement; unbind clears the active context and bounds, and a new event bind atomically replaces both. A same-generation bind is allowed only as one reassertion on a newly acknowledged End Event stream immediately following stream replacement and only for the exact still-active event UUID/generation retained across that replacement; it does not lower or advance the high-water mark. `CONTEXT_UNBIND` clears the active context, bounds, and any reassertion allowance while retaining the high-water mark, so a same-generation bind after unbind is rejected. A different event UUID can replace the current context only through a signed bind; its generation must exceed a retained high-water mark if that UUID appeared earlier. On event start and every generation transition, the server sends `CONTEXT_BIND` before any event mutation. On event termination, it sends `CONTEXT_UNBIND` before clearing `eventId`; connection loss relies on client connection cleanup. High-water marks reset only on disconnect or server switch, so a new connection may accept the prior event UUID/generation again. A connection retains at most 64 event UUID high-water entries; exceeding this limit fails closed for new binds until reconnect.

A Narcotics body is one fixed record in this order: `u8 schema=1`, `u8 type`, `u32 message_schema=4`, `i64 command_seq`, `i64 body_timestamp_ms`, `session_uuid[16]`, `string effect_id`, `string shaderpack_id`, `u32 duration_ms`, `f32 intensity` (finite, 0..1), `u32 fade_in_ms`, `u32 fade_out_ms`, `string mode`, `string clear_policy`, `string source`, `string reason`, `string status`, `uuid visual_instance_id` (zero UUID only where unused), `uuid target_visual_instance_id` (zero UUID only where unused), and `i64 clear_through_counter` (zero only where unused). The timestamp must equal the outer `issued_at_ms`; `visual_start` duration is 1,000..600,000 ms, while `visual_stop` and `visual_clear_all` require duration, intensity, fade-in, and fade-out all to be zero; each fade is at most 10,000 ms. Session UUID must match the active client-mod session for that recipient. `command_seq` is a positive per-recipient, per-verified-session Narcotics sequence allocated by one monotonic allocator shared by every start, refresh, stop, and clear-all command; it is independent of the signed stream counter. A start command's sequence is also its `ClientVisualCommand.seq`; stop and clear-all commands receive their own sequence and correlation record. A retransmission preserves command sequence, instance ID, and all logical body fields while using a fresh signed envelope counter and timestamp; the same `command_seq` and type must match the original command in every body field except `body_timestamp_ms`, and the envelope counter/timestamps are not part of logical duplicate comparison. A deliberate refresh preserves the visual instance ID and uses a new command sequence. The allocator never wraps: if the next command would exceed `Long.MAX_VALUE`, it fails closed for that recipient until a new verified client-mod session. The client stores one map entry per `(Narcotics stream ID, visual_instance_id)` containing effect ID, command sequence, latest accepted start counter, and runtime. Exact duplicate logical commands are idempotent and re-acknowledged only while their receipt remains in the bounded command ledger; the same retained command sequence with a different type or any changed logical field is rejected and retires only the Narcotics sender stream. Repeated commands are checked before side effects: retries never reapply a clear fence or start a second runtime, and the client leaves current state unchanged. Capability fields and effect-advertisement lists are not present in v4 mutation bodies. Type codes are `1 visual_start`, `2 visual_stop`, and `3 visual_clear_all`; all unused strings are empty and unused numeric fields are zero.

The command ledger is keyed to the current recipient, local connection epoch, and verified client-mod session; it survives Narcotics stream rotation and resets on disconnect, server switch, or verified-session replacement. It is independent of the active visual map and server-side `ClientVisualCommandCorrelation`, which correlates client reports. The ledger retains at most 256 accepted sequence receipts, evicting the oldest receipt when full while retaining the highest accepted `command_seq`. Each receipt stores the command type, a SHA-256 fingerprint of the exact logical body bytes with only `body_timestamp_ms` omitted, and the original client response tuple (report kind, status, reason, and effect ID). A sequence greater than the high-water mark is a new command; gaps are allowed for stream-rotation snapshots. A matching sequence still in the ledger with the same type and fingerprint replays the original response tuple and has no side effects, including for `visual_stop` or `visual_clear_all` after the affected visual has already been removed. A matching retained sequence with a different type or fingerprint rejects the packet and retires only the Narcotics sender stream. A sequence at or below the high-water mark whose receipt was evicted is stale: reject it without applying effects or replaying a report, and do not retire the stream. New command sequences must be strictly greater than the high-water mark. Ledger capacity never permits an old command to be treated as new.

The server-side `ClientVisualCommandCorrelation` is a separate bounded report-correlation store, keyed by recipient, verified client-mod session, active Narcotics stream, and `command_seq`; it retains at most 512 records per recipient/session. A command retry uses the exact same logical command sequence and fields with a fresh body timestamp/envelope, only while the same sender stream remains active, no valid report has arrived, less than 30 seconds have elapsed since first send, and fewer than 256 newer unique visual commands have been issued for that recipient/session. Stop retrying when any condition ends; never retry an evicted or retired-stream command. If delivery remains unknown after the retry window, re-evaluate desired visual state and, if still needed, issue a newly allocated `command_seq` with a newly constructed command: refresh the same visual instance for a start, target the same instance for a stop, or compute a new clear fence for clear-all. On stream rotation, invalidate correlations from the retired stream and send the current visual snapshot with fresh command sequences on the replacement stream. Delivery correlation for an unacknowledged command expires after 30 seconds; a start's valid `STARTED` ACK transitions its record to lifecycle report correlation through `body_timestamp_ms + duration_ms + 30,000 ms` (at most 630,000 ms). A valid `STOPPED` or `CLEARED` ACK retires its stop or clear-all record; terminal `visual_finished`/`visual_error` reports retire their matching start records. Unacknowledged stop/clear correlations expire after 30 seconds. Prune expired records before insertion; if the 512-record cap is still full, fail closed for new visual sends until records expire or the sender stream is rotated. Clear all records on verified-session replacement or disconnect.

- `visual_start` has a fresh nonzero `visual_instance_id` for a new logical effect, plus the validated effect/shaderpack and visual parameters. A refresh or retransmission retains the same instance ID but uses a fresh outer counter and timestamp. `effect_id` is one of `DESATURATE`, `COLOR_CONVOLVE`, `SCAN_PINCUSHION`, `GREEN_NOISE`, `INVERT`, `WOBBLE`, `BLOBS`, `PENCIL`, `CHAOS`, `OVERDOSE`, or `ZHUZEVO_TRIP`. `shaderpack_id` is empty or exactly one of `trippy_shaderpack.zip`, `ctr_vcr.zip`, `cursed_metamorphopsia.zip`, `lsd_shader.zip`, `crucify.zip`, `nms_1_6.zip`, `acid_shaders.zip`, or `white_sharp_1_2.zip`. `mode` is exactly `CLIENT_MOD`; `clear_policy` is `REPLACE_ALL_FULLSCREEN` or `PRESERVE`; `source` is 1-32 bytes matching `[A-Za-z0-9_.:-]+`; `reason` and `status` are empty. For `REPLACE_ALL_FULLSCREEN`, the initial command's `clear_through_counter` must equal its envelope counter minus one and the client excludes the current `visual_instance_id` from the clear fence; retries preserve this original fence, which must remain less than the retry envelope counter. For `PRESERVE` it is zero. The client retires only remote visuals owned by this Narcotics stream whose latest accepted start counter is at or below that fence; a same-ID refresh updates its existing runtime. A duplicate retry acknowledges the original command and does not update its latest accepted start counter. Local test visuals and End Event visuals are outside this operation.
- `visual_stop` uses `target_visual_instance_id` for the exact instance and requires `effect_id` to match the target. `mode` is exactly `CLIENT_MOD`; `clear_policy`, `source`, and `status` are empty; `reason` is 1-256 bytes matching `[A-Za-z0-9_.:-]+`. It never stops all visuals sharing an effect name. A missing or already finished target is an idempotent no-op.
- `visual_clear_all` has nonzero `clear_through_counter`; on the initial command it equals the envelope counter minus one, and retries preserve that original fence while requiring it to be less than the retry envelope counter. `mode` is `CLIENT_MOD`, `clear_policy` is `REPLACE_ALL_FULLSCREEN`, `source` is `SYSTEM`, and `reason` is 1-256 bytes matching `[A-Za-z0-9_.:-]+`; effect ID, shaderpack ID, status, duration, intensity, and fades are empty or zero. It clears only Narcotics remote visuals owned by this exact stream whose latest accepted start counter is at or below the fence. It cannot clear local test visuals or End Event state.

The server signer serializes each player's sender stream and body dispatch in the same order. A visual's last accepted start counter is updated on every signed refresh. Thus a delayed clear cannot erase a later start even if a client task reaches the main thread after that start. Stream replacement first retires the old stream's visuals, then accepts mutations from the new authenticated stream. Each server stream allocates its next outer counter only inside its serialized send queue immediately before signing and enqueuing the packet. If signing, serialization, or enqueueing fails after allocation, retire that stream and require a fresh stream; never skip ahead on the existing one. Counters do not wrap; before exhaustion, retire and replace the stream, subject to the 256-stream per-connection limit.

The outer v4 envelope is a strict binary record in big-endian order: unsigned protocol version byte (`4`); one-byte key-ID byte length and ASCII key ID; one-byte nonce length and the 43 ASCII nonce bytes; 16-byte recipient UUID (most-significant then least-significant 64-bit value); one-byte stream-ID length and the 22 ASCII stream-ID bytes; positive signed 64-bit counter; signed 64-bit issued-at epoch milliseconds; signed 64-bit expiry epoch milliseconds; unsigned 32-bit body length; exact body bytes; and exactly 64 raw signature bytes. There are no optional fields or trailing bytes. The exact binary bodies and message schemas above are parsed only after signature verification. Parsing rejects malformed encodings, duplicate fields where a bounded list is used, missing or non-default reserved values, unknown message types, and out-of-range values. No component normalizes or reserializes body bytes before verification. The nonce and stream ID must decode as canonical Base64URL without padding to exactly 32 and 16 bytes respectively and re-encode byte-for-byte to the received ASCII form. Protocol-v1 signatures and envelopes are always rejected by the v4 client.

The envelope parser checks lengths before allocation: key ID is 1-64 ASCII bytes and must equal the pinned key ID; nonce and stream ID have the exact encodings above; body size is 1-65,536 bytes; and the signature is exactly 64 raw bytes. The exact Ed25519 input is: u32 byte length plus ASCII bytes for domain `copimine:client-bridge:v4`; u32 canonical format version `1`; u8 protocol version `4`; u32 byte length plus ASCII key ID; u32 byte length plus ASCII nonce; recipient UUID as 16 bytes in most-significant then least-significant order; u32 byte length plus ASCII stream ID; i64 counter; i64 `issued_at_ms`; i64 `expires_at_ms`; u32 body byte length; and the exact body bytes. Every integer and length is big-endian; all length prefixes in the signing input are unsigned 32-bit values. This is the versioned BridgeSigningPolicy canonical format; the raw signature is not part of the signed input. Issued-at and expiry are positive epoch milliseconds; expiry must follow issued-at, validity is at most 60 seconds, and issued-at may be at most 30 seconds in the future. A packet is expired when now is greater than or equal to expiry. The implementation must not try the current v1 domain or any legacy canonical encoding when v4 verification fails.

The client accepts an acknowledgement only when its key ID and signature match the pinned key, its nonce matches the current connection, its recipient is the current player, its body names a known sender, its request kind and ID match the one outstanding request, its counter is exactly 1, and its stream ID has never been seen for this connection. For that stream it accepts only the next counter in order, with valid timestamps, a valid signature, and a well-formed bounded body. A validly signed counter gap or authenticated malformed body retires that stream; only a fresh signed acknowledgement on a new stream can resume that sender. Invalid signatures, wrong-key IDs, wrong recipients, wrong nonces, replayed counters, stale messages, and expired or future-dated envelopes are dropped without changing client feature state or retiring a stream. Once an in-order signed envelope passes signature and freshness checks, its body is decoded; a malformed body retires that authenticated stream without dispatching the body. Verification and counter advancement happen before dispatch; a single per-connection main-thread queue applies packets in order and rechecks the never-reused local connection epoch, nonce, player UUID, active stream, and expiry at apply time. If an already accepted packet expires while queued, the client discards it and retires that sender stream before applying later queued messages. Wrong-key, wrong-recipient, wrong-nonce, unknown sender, unacknowledged or retired stream, skipped, stale, duplicate, expired, future-dated, tampered, malformed, unbound or mismatched event-generation, and unsigned v3 mutation packets produce no client feature-state mutations. A validly signed gap or body failure may retire only its authenticated sender stream as specified above.

The retained v3 client-to-server visual responses are untrusted delivery reports, not control authority. Each `visual_ack`, `visual_finished`, or `visual_error` must match the live verified player/session, the exact positive v4 `command_seq`, the command type, and the exact expected `effect_id`; for `visual_clear_all`, the expected effect ID is empty. `visual_ack` status is exactly `STARTED` or `STARTED_<route-token>` for a start, `STOPPED` for a stop, or `CLEARED` for a clear-all (total <=32 ASCII bytes; route token matches `[A-Z0-9_-]{1,24}`). Accept ACK correlations for starts, refreshes, stops, and clear-all; `visual_finished` is for a running start command and carries the exact effect ID, bounded reason, and empty status; `visual_error` is for a start command and carries the exact effect ID, bounded reason, and status `ERROR`. Every accepted report has protocol 3, the exact current session, mode `CLIENT_MOD`, source `SYSTEM`, empty client version/shaderpack/clear policy, false capability flags, zero duration/intensity/fades, and an empty supported-effect list; any other field is ignored. Their current protocol-v3 payload remains on `copimine:client_bridge`. These reports may update delivery diagnostics and client-visual fallback/cleanup only. They cannot apply damage, grant rewards, change event progress, authorize prisoner abilities, skip server-side permission/cooldown/target checks, or decide any End Event outcome. A v3 PING confirms only the v3 client-mod handshake, never either v4 sender's readiness.

## Protected message scope

Authenticate every mutating server-to-client `END_EVENT:*` packet and Narcotics `visual_start`, `visual_stop`, and `visual_clear_all` packet. Do not authenticate client-to-server capability claims as server authority; the server still validates each player ability request against its existing event, generation, player, cooldown, and target rules, and additionally checks the current client nonce/session.

When the Paper signer is unavailable, do not send unsigned controls or visuals. Server mechanics that depend on client-side prisoner or control state must not start for that client. Other event gameplay can continue only where it does not rely on a protected client mutation.

## Server key loading

Both Paper senders use the same v4 protocol policy and call the Narcotics-owned signer service. The loader reads Base64 PKCS#8 from the external file named by COPIMINE_CLIENT_BRIDGE_PRIVATE_KEY_FILE. Before reading the whole file it enforces a maximum size of 4,096 bytes; it accepts only ASCII Base64 with at most one terminal LF or CRLF and no internal whitespace, decodes at most 512 bytes, parses in memory, and wipes the decoded byte array after key construction. It signs a fresh random startup challenge and verifies it against the pinned public key and configured fingerprint before publishing a signer. The in-memory key object lives only for the running Narcotics plugin instance. It never emits key bytes, encoded key text, path, or key material in exception messages or logs. There is no fallback key or v1 signer. An invalid or unavailable key disables protected sends and reports a generic state without exposing the path or contents. Deployment must provision the external file with an ACL granting the Paper service identity read/traverse access only, while SYSTEM and local Administrators may manage the key. No untrusted principal may write, modify, delete, replace, or change the ACL of the key file or any parent directory in a way that permits replacement; verify effective file and parent-directory permissions without opening key contents. The loader does not infer or silently repair ACLs. The server-side ClientModSessionRegistry is published by Narcotics only after its pending v3 challenge is accepted, uses a non-reused per-connection epoch, and is invalidated on quit, handshake rejection, version-policy change, shutdown, and fresh challenge replacement. End Event treats an unavailable registry or signer as no authenticated client and keeps only protected client-dependent mechanics disabled.

## Rollout and limits

Deploy compatible v4 clients and both Paper signers together. Until both server senders can sign with the matching external key, protected controls and visuals remain unavailable; the client must not fall back to v3. The trust model identifies possession of the dedicated CopiMine private key, not a particular network hostname. Keep production deployment and secret provisioning separate from source changes.
